# API Contract: Frontend and Backend

**Status:** DRAFT v0.2. Endpoint names and shapes are **proposed** from `docs/SPEC.md` and decisions D-001, D-010 and D-011. Both roles review and then freeze them before building against them.

## 1. How this contract works

- **Two files, one truth.** `contract/openapi.json` (generated from the backend) holds the exact shapes. This document holds the conventions, meanings and rules that a schema cannot express. If they differ, the OpenAPI file wins for shapes and this file wins for meaning. Fix the difference in the same pull request.
- **Contract first.** The backend publishes or updates `contract/openapi.json` before implementing an endpoint. The frontend builds against it, using mocks from `contract/fixtures/` until the endpoint exists.
- **Fixtures.** Every endpoint has at least one fixture per outcome (success, partial, failed, empty). The frontend mocks and the backend contract tests use the **same** fixtures. A fixture marked `"planned": "<work package>"` publishes an agreed shape before its endpoint exists; its bodies are checked against the schema like any other, and the mark is removed when the endpoint is built.
- **Who may change it.** Either role may propose a change by pull request. The other role must approve it. Neither role merges contract changes alone.
- **Breaking changes** (removing or renaming a field, changing a type or meaning, changing an enum value) need a new version prefix or a coordinated release. Adding an optional field is not breaking.

## 2. Conventions

| Topic | Rule |
|---|---|
| Base path | `/api/v1` |
| Format | JSON, `camelCase` field names, UTF-8 |
| IDs | UUID strings |
| Time | ISO 8601 in UTC (`2026-10-20T08:30:00Z`) |
| Auth | `Authorization: Bearer <accessToken>`. The refresh token is an `httpOnly`, `Secure`, `SameSite` cookie. The frontend keeps the access token in memory only. |
| Silent refresh | On `401` with `code: TOKEN_EXPIRED`, call `POST /auth/refresh` once, retry the original request once, then go to login |
| Pagination | Cursor based: `?cursor=&limit=`; response `{ items, nextCursor }` |
| Long work | Analyses run server side. The client starts one and **polls** `GET /analyses/:id` every `pollAfterMs` while `status` is `running`. Leaving the screen never cancels it. |
| Duplicates | Starting an analysis for the same user, edition and taste-profile version while one is running returns the existing one |
| Ownership | Every user-owned resource is checked server side. Another user's id returns `404`, never `403`, so existence is not leaked. |
| Review text | Always untrusted. Render as plain text. |
| Health check | `GET /health` (outside `/api/v1`) returns `{ status: 'ok' }` and no data. It is public for Docker and CI: the only exception to SEC-2 besides `/auth/*` |
| Generated shapes | `contract/openapi.json` is generated by `pnpm generate` and checked in CI by `pnpm generate:check`. A test fails if section 2 or 3 of this file disagrees with the code |

### Error format (every non-2xx response)

```json
{ "code": "SCAN_QUOTA_EXCEEDED", "message": "Scan limit reached.", "retryable": true, "retryAfterSeconds": 3600, "fields": { } }
```

`message` is a safe default. The frontend maps `code` to its own wording. `fields` is present only for `VALIDATION_FAILED` (field name to message).

| Code | HTTP | Meaning |
|---|---|---|
| `VALIDATION_FAILED` | 400 | Input rejected, see `fields` |
| `UNAUTHENTICATED` | 401 | No or invalid credentials |
| `TOKEN_EXPIRED` | 401 | Access token expired, refresh once |
| `INVALID_CREDENTIALS` | 401 | Same message for unknown email and wrong password |
| `NOT_FOUND` | 404 | Missing, or not yours |
| `RATE_LIMITED` | 429 | Too many requests, see `retryAfterSeconds` |
| `SCAN_QUOTA_EXCEEDED` | 429 | Per-user scan quota used up |
| `UPLOAD_TOO_LARGE`, `UNSUPPORTED_TYPE` | 413, 415 | Rejected before processing (DISC-4) |
| `NOT_A_BOOK`, `UNREADABLE_IMAGE` | 422 | Scan dismissed; the UI offers typed search |
| `IDENTIFICATION_UNAVAILABLE` | 503 | Vision service down or out of quota; typed search still works |
| `SOURCES_UNAVAILABLE` | 503 | All sources failed. Never reported as 'no reviews'. |
| `LLM_QUOTA_EXHAUSTED` | 503 | Cached results still served; retry later |
| `INVALID_MODEL_OUTPUT` | 502 | A step failed after its one retry |
| `MODEL_UNAVAILABLE` | 503 | No taste model is shipped yet, so the personal match cannot be scored. Used only as a step `errorCode` (D-021); the public reception is unaffected |
| `CONFLICT` | 409 | State conflict (for example, import already confirmed) |
| `EMAIL_IN_USE` | 409 | Register only: the email already has an account (accepted trade-off, D-001) |
| `INTERNAL_ERROR` | 500 | Unexpected server error. Details are logged on the server, never returned |

## 4. Endpoints (proposed)

### 4.1 Authentication
(Custom email and password, decided in D-001. Email verification, account lockout and refresh-token family tracking are out of scope for v2. Every `/auth/*` endpoint is public; every other endpoint needs a valid access token (SEC-2). Register, login and forgot-password are throttled and can return `RATE_LIMITED`.)

| Method and path | Request | Response |
|---|---|---|
| `POST /auth/register` | `{ email, password, displayName }` | `201 { accessToken, expiresInSeconds, user }` plus refresh cookie (signed in right away). `409 EMAIL_IN_USE` if the email is taken. Password 10 to 128 characters (configurable). |
| `POST /auth/login` | `{ email, password }` | `{ accessToken, expiresInSeconds, user }` plus refresh cookie |
| `POST /auth/refresh` | cookie | `{ accessToken, expiresInSeconds }` plus a new refresh cookie. The old refresh token is revoked (rotation on every use). |
| `POST /auth/logout` | cookie | `204` |
| `POST /auth/forgot-password` | `{ email }` | `202`, identical for known and unknown emails |
| `POST /auth/reset-password` | `{ token, newPassword }` | `204`. All existing sessions become invalid, including access tokens already issued. An invalid, used or expired link returns `400 VALIDATION_FAILED` with `fields.token`. |

`User` = `{ id, email, displayName, onboardingState }`, where `onboardingState` is `pending`, `skipped` or `completed`.

**Session rules the frontend relies on (BE-3)**
- The refresh cookie is `bookie_refresh`: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/api/v1/auth`. JavaScript never sees it. Send auth requests with `credentials: 'include'`.
- Refresh tokens rotate on every use, so a refresh token works once. Run one refresh at a time (share the in-flight request between tabs or calls); a second, parallel refresh with the same cookie gets `401 UNAUTHENTICATED`.
- On page load there is no access token in memory: call `POST /auth/refresh`, then `GET /me` for the user.
- `401 TOKEN_EXPIRED` means refresh once and retry. `401 UNAUTHENTICATED` means go to login.
- `POST /auth/forgot-password` returns `202` with no body for every email.
- The reset email links to `{WEB_ORIGIN}/reset-password#token=<token>`. The token is in the URL fragment, which browsers never send to a server. The page reads it and posts it to `POST /auth/reset-password`. The link expires after 30 minutes by default and works once.
- Register, login and forgot-password are throttled per IP and per email (default 10 per 15 minutes each) and return `429 RATE_LIMITED` with `retryAfterSeconds`.

### 4.2 Taste capture

Every save (rating, removal, questionnaire, confirmed import) creates a new immutable taste-profile version, numbered from 1 per reader. A save that changes nothing creates no version. `tasteProfileVersion: 0` means the reader has never saved anything.

| Method and path | Request | Response |
|---|---|---|
| `GET /taste-profile` | none | `{ version, ratedCount, minForConfidence, hardFloor, questionnaire: { likedGenres, dislikedGenres, pace, themesToAvoid }, createdAt }` (`minForConfidence` default 10, `hardFloor` default 3, both from server config). Unanswered questionnaire fields are `null`. |
| `GET /ratings?cursor=&limit=` | query | `{ items: [Candidate + { rating, origin: 'quick_rate' \| 'imported' }], nextCursor }`: the current version's ratings, by title. `limit` 1 to 200, default 50. |
| `PUT /ratings/:editionId` | `{ rating: 1 to 5 }` | `{ tasteProfileVersion, ratedCount }`. `404` for an unknown edition. |
| `DELETE /ratings/:editionId` | none | `{ tasteProfileVersion, ratedCount }`. Removing a book that is not rated changes nothing. |
| `GET /catalog/search?q=&limit=` | query | `{ items: [Candidate + { yourRating }], external }` for the Quick rate list. Without `q`: the most-rated books. With `q`: the same search as 4.3, more results (default 20, at most 50). `yourRating` is the reader's current rating or `null`. |
| `POST /ratings/import` | multipart, field `file`: a Goodreads or StoryGraph CSV export, at most 10 MB by default | `202 { importId }`. Rows are matched in the background. |
| `GET /ratings/import/:importId` | none | `{ importId, status, format, totalRows, matchedCount, ignoredRows, unmatched: [{ rowIndex, rawTitle, rawAuthor, rating, candidates: [Candidate] }] }`. `status`: `processing`, `needs_review`, `confirmed`, `failed`. `unmatched` is filled once `status` is `needs_review`. |
| `POST /ratings/import/:importId/confirm` | `{ resolutions: [{ rowIndex, editionId } \| { rowIndex, skip: true }] }` | `{ tasteProfileVersion, ratedCount }` |
| `GET /questionnaire/options` | none | `{ genres: [string], themes: [string], paces: ['slow', 'moderate', 'fast'] }` |
| `PUT /questionnaire` | `{ likedGenres, dislikedGenres, pace, themesToAvoid }` (D-011). Any field may be `null` or left out for unknown. `themesToAvoid` = `[{ theme, sensitivity: 'high' \| 'moderate' \| 'low' }]`; a theme not listed is unknown. Replaces all four answers; ratings are kept. | `{ tasteProfileVersion, ratedCount }`. **Unknown is never a dislike.** |
| `POST /onboarding/skip` | none | `204`. The reader's `onboardingState` becomes `skipped` (D-002). `409 CONFLICT` if skipping is turned off. Saving any taste input sets it to `completed`. |

**Import rules the frontend relies on (ONB-1)**
- Poll `GET /ratings/import/:importId` until `status` is not `processing` (usually a few seconds).
- `matchedCount` rows were matched without asking (Goodreads book id, ISBN, or exactly one book with that title and author). `unmatched` rows need the reader: pick one of the `candidates`, search for the book (4.3) and send its `editionId`, or skip.
- Rows left out of `resolutions` are skipped on confirm; they were listed, so nothing is dropped silently.
- `ignoredRows`: rows in the file with no rating (for example "to-read"). Say how many.
- Imported ratings replace earlier ratings of the same book. StoryGraph quarter stars are rounded to whole stars (halves up).
- Errors: `400 VALIDATION_FAILED` with `fields.file` (not a known export, no rated books, too many rows), `413 UPLOAD_TOO_LARGE`, `415 UNSUPPORTED_TYPE` (not a text file), `429 RATE_LIMITED` (default 10 imports a day). Confirming twice, or before matching ends, is `409 CONFLICT`.
- The file is read in memory. Only title, author and rating are kept; reviews, notes, shelves and dates are never stored.

**Version rules (ONB-4):** earlier versions never change. An analysis made with an older version is outdated; the analysis API reports this as `isOutdated` (4.4).

### 4.3 Discovery

`Candidate` = `{ editionId, title, subtitle, author, year, language, publisher, format, coverUrl }`. Every field except `editionId` and `title` may be `null` when unknown (DISC-1: show all available identifying fields). `author` lists the main authors, comma-separated; illustrators and translators are left out. `language` is a BCP 47 tag.

| Method and path | Request | Response |
|---|---|---|
| `GET /books/search?q=` | query: title, author, both, or an ISBN (2 to 200 characters) | `{ candidates: [Candidate], external }`. At most 3 candidates (`SEARCH_MAX_CANDIDATES`), **one per book**: different editions of the same work are not shown side by side; the edition with the most dataset reviews is chosen. Never auto-selects. |
| `POST /scan` | multipart, field `image`: JPEG or PNG, already resized by the client (default 1024 px), at most 2 MB by default | `{ outcome: 'identified' \| 'uncertain', candidates: [Candidate], recognized: { title, subtitle, authors }, external }`, or an error. |

`external` is `null` when only the catalog was searched, or `{ source: 'open_library', outcome }` (`sourceOutcome`) when Open Library was asked because the catalog had no good match. Books found there are added to the catalog, so their candidates have an `editionId` like any other.

**Meaning rules the frontend relies on**
- `candidates: []` with `external.outcome = 'failed'` or `'rate_limited'` means the book may exist but a source could not be checked. Say so; do not say "no such book".
- `outcome = 'identified'`: exactly one book matched what the cover says, and the cover was read clearly. The reader still confirms the candidate before an analysis starts.
- `outcome = 'uncertain'` always goes to the confirmation screen (DISC-2), even with one candidate. With no candidates, offer a typed search prefilled from `recognized`.
- Errors before processing (DISC-4): `413 UPLOAD_TOO_LARGE`, `415 UNSUPPORTED_TYPE` (the type is checked from the file's content, not its name). `422 UNREADABLE_IMAGE` for a broken file. None of these use up a scan.
- `422 NOT_A_BOOK`, `422 UNREADABLE_IMAGE`: dismiss with a prompt to type the title. These use up a scan.
- `503 IDENTIFICATION_UNAVAILABLE`: the vision service is down or out of quota. Typed search still works. The scan is given back.
- `429 SCAN_QUOTA_EXCEEDED`: `SCAN_DAILY_QUOTA` scans (default 20) in any 24 hours; `retryAfterSeconds` says when the next one is free.
- Search is limited per reader (default 60 a minute) and can return `429 RATE_LIMITED`.
- The photo is processed in memory and never stored (DISC-3). Its metadata (EXIF, including location) is removed before it is sent to the vision model.

### 4.4 Analyses

**Status: agreed 2026-10-21** (D-019; approved by the owner for both roles). Built in BE-8 (D-021). Shapes and paths are in `contract/openapi.json` (`Analysis`, `AnalysisSummary`, `AnalysisList`, `StartAnalysis`, `RetryAnalysis`); examples of every outcome are in `contract/fixtures/analyses-*.json`.

| Method and path | Request | Response | Errors |
|---|---|---|---|
| `POST /analyses` | `{ editionId, refresh? }` | `201 Analysis` (new), or `200 Analysis` when the reader already has one running for this edition and taste-profile version (joined, not duplicated). With `refresh: true` the public reception is built again even if a fresh one exists (spec 10 user refresh); if that build fails, the older reception is shown as `stale` (PERF-3) | `400`, `404` unknown edition, `429` (also when the reader used today's refreshes of this book, `REFRESH_PER_BOOK_PER_DAY`, with `retryAfterSeconds`) |
| `GET /analyses/:id` | none | `Analysis` | `404` |
| `POST /analyses/:id/retry` | `{ steps?: [stepName] }` (all failed steps when left out) | `200 Analysis`, running again. Done steps are never repeated (RES-2) | `400` a step that did not fail, `404`, `409` nothing failed or still running, `429` |
| `POST /analyses/:id/recalculate` | none | `201 Analysis`: a new analysis for the current taste profile, with `recalculatedFromId`. The old one is unchanged | `404`, `409` already uses the current profile, `429` |
| `GET /analyses` | `?cursor=&limit=` | `AnalysisList`: `{ items: [AnalysisSummary], nextCursor }`, newest first (history) | none beyond auth |

The separate evidence endpoint in v0.2 is dropped: the evidence a section cites is inside the `Analysis` (see below).

**`AnalysisSummary`** (a history row): `id`, `status`, `createdAt`, `finishedAt`, `edition` (a `Candidate`), `publicReception` with `status`, `stale`, `evidenceState`, `summary` and `evidenceConfidence`, `personalMatch` with `status`, `score`, `scale`, `modelId`, `isFallback`, `evidenceConfidence`, `tasteProfileVersion`, `currentTasteProfileVersion` and `isOutdated`, and `feedback`. No evidence, claims or traits.

**Meaning rules the frontend relies on.** The `Analysis` schema checks the starred rules (★) in code, so the backend's output and the fixtures cannot break them.

*Status and progress*
- `status`: `running` while any step is pending or running; `complete` when everything that applies is done; `partial` when the public reception is shown with something missing (limited or insufficient evidence, the personal match failed, or an older reception is shown because building a newer one failed); `failed` when no public reception can be shown (all sources failed, or a public step failed after its retry).
- ★ `pollAfterMs` is set exactly while `running`: poll `GET /analyses/:id` after that long, and stop when it is null. ★ `finishedAt` is set exactly when the analysis is no longer running. Leaving the screen never cancels (RES-1).
- ★ `steps` always lists all eight steps in `stepName` order, for the progress rail (D-010 point 7). ★ `errorCode` is set exactly on failed steps (an error code from section 2).
- ★ `canRetry` is true only when a step failed and `POST /analyses/:id/retry` will run it again. Show retry only when it is true.

*Public reception*
- `publicReception.status` uses `stepStatus` (never `skipped`). ★ Summary, praises and complaints are present only once it is `done`.
- ★ `summary = null` with `evidenceState = insufficient`: no written verdict exists. Do not display placeholder prose that looks like one (RES-3).
- ★ `evidenceState = unavailable` means every source failed: the analysis is `failed`, with retry. It is **never** presented as "no reviews" (RES-4).
- `sources` lists every source asked, with its outcome, so failures are disclosed (spec 11). Show the rating average and count per source, named by `name`; no combined public score (D-010 point 3). `ratingScope = work` means the rating covers every edition of the book: label it so. `providesText = false` marks rating-only sources. `fetchedAt` dates older data (PERF-3).
- ★ `evidence` holds exactly the items cited by `praises`, `complaints` and both `traits` lists, so every `evidenceIds` entry resolves within the response (RES-5). `number` is the stable "Review #12" label. `excerpt` is untrusted text of at most 1,000 characters: render it as plain text. ★ `excerpt` is null when `displayAllowed` is false; it is also null for `source_aggregate` items, which stand for `reviewCount` reviews. The book description can be cited (`kind = description`, `source = null`).
- `traits` describe the book (D-015 vocabularies). Empty `values` means unknown, and ★ an unknown trait cites nothing.
- ★ `stale = true` (PERF-3, D-025): building a newer reception failed (a refresh, or a rebuild after expiry), so an older one is shown. Label it with its date (`generatedAt`), for example "Reviews as of 21 Oct 2026; updating them failed". The failed step has its `errorCode` and `canRetry` is true; the analysis is `partial`, never `failed`. The personal match still runs.

*Personal match*
- `personalMatch.status = needs_taste_data`: no taste profile yet. Show the invitation to rate books (ONB-2). `score` is null.
- `personalMatch.status = below_floor`: fewer than `hardFloor` rated books. **No score is shown** (MODEL-4); say how many books are rated (`ratedCount`) and how many are needed.
- `running` covers both waiting and running; `failed` comes with `errorCode` and, if retryable, `canRetry`; `skipped` means a step it needs failed.
- `failed` with `errorCode = MODEL_UNAVAILABLE`: the reader has enough rated books, but no taste model is shipped yet (D-021). Say personal matching is not available yet; `canRetry` stays false until a model ships.
- ★ `score` is set exactly when `status = done`. ★ It is on `scale` (1 to 5) and already rounded to one decimal: display it as given, for example "4.2 / 5", never as a percentage (D-007, D-010).
- ★ A score always comes with `modelId`, `modelVersion` and `evidenceConfidence` (MODEL-3). ★ `isFallback = true` means B0 or B1 produced it (cold start, or a book the learned model does not know, D-024), and its confidence is always `low`: show the score, label it low confidence, and name the fallback model.
- Explanations come from the model (spec 7). ★ They exist only with a score. `similarRatedBooks` are the reader's rated books most similar to this one. `traits` group as: `aligned` → "Why it fits", `conflicting` → "Things to keep in mind", `unknown` → "Not factored in". For `unknown`, empty `yourValues` means the reader has no preference on record, and empty `bookValues` means the book's trait is unknown. Unknown preferences never affect the score (MODEL-2).
- `isOutdated` is computed by the server when read (ONB-4). ★ When true, `currentTasteProfileVersion` is newer than `tasteProfileVersion`: show the recalculate banner with both numbers.
- A personal failure never removes the public reception (RES-7).

*Everything else*
- All three signals stay separate fields. No combined score or combined verdict label exists anywhere (D-010). Evidence confidence is only `level` plus `reasons`; there is no numeric confidence score.
- `edition` is the edition analysed, so the screen can name it (DISC-5).
- `feedback` holds the reader's current choice per section, or null. ★ It is null on sections that were not generated; hide the buttons there (spec 6, Feedback).
- Elements of the result and history mockups with no field here are not shown: "Critical score", percentages, "/100" numbers, consensus labels, "access type", reviewer names and publication bylines, "sensitivity noted" badges (D-010).

### 4.5 Feedback, lists, account

**Status: agreed 2026-10-21** (D-022; approved by the owner for both roles). Built in BE-10. Shapes are in `contract/openapi.json` (`FeedbackRequest`, `FeedbackSaved`, `ReadingList`, `ReadingListAdd`, `ReadingListEntry`, `Comparison`, `DeleteMyDataRequest`); examples of every outcome are in `contract/fixtures/` (`feedback-put`, `reading-list-get`, `reading-list-add`, `reading-list-delete`, `compare`, `me-data-delete`).

| Method and path | Request | Response | Errors |
|---|---|---|---|
| `PUT /feedback` | `{ analysisId, target, value }` | `200 { target, value, updatedAt }`. One value per reader, analysis and target; saving again replaces it (FB-1) | `400`, `404` not the reader's analysis (FB-2), `409` that section failed or was not generated |
| `GET /reading-list` | none | `ReadingList`: `{ items: [{ edition, addedAt, analysisId, group, personalMatch }] }` in the order to show | none beyond auth |
| `POST /reading-list` | `{ editionId }` | `201 { editionId, addedAt }` added, or `200` with the same body when it was already on the list | `400`, `404` unknown edition |
| `DELETE /reading-list/:editionId` | none | `204`, also when the book was not on the list | `404` not an id |
| `GET /compare?a=&b=` | two analysis ids | `Comparison`: `{ a: Analysis, b: Analysis, traitDifferences: [{ trait, a, b }] }` | `400` missing id or the same id twice, `404` either one missing or not the reader's |
| `GET /me` | none | `User`: the signed-in reader only (SEC-1) | none beyond auth |
| `DELETE /me/data` | `{ password }` | `204`. The reader stays signed in and starts onboarding again | `400` wrong password (`fields.password`), `429` too many attempts |

**Meaning rules the frontend relies on.** The `ReadingList` schema checks the starred rules (★) in code.

*Feedback*
- Show the buttons only on a section whose status is `done` (`publicReception.status` for the public reception, `personalMatch.status` for the personal match); hide them on sections that are running, failed or were not generated. `feedback.public` and `feedback.personal` are the saved choices, null until the reader picks one, so they do not say whether to show the buttons. A `409` means the section is not there to judge; do not retry.
- Feedback is stored with the analysis, its taste-profile version and, for the personal match, the model version that produced the score (spec 6). Read it back from `Analysis.feedback`.

*Reading list*
- `edition` is a `Candidate`. `analysisId` is the reader's latest **finished** analysis of that edition, or null; open it for the full result. `personalMatch` is that analysis's match as in `AnalysisSummary`, or null when there is none.
- ★ `group` says how the item is placed (LIST-2): `ranked` (a score with medium or high confidence from a learned model), `low_confidence` (a score with low confidence, including the fallback models B0 and B1), `no_match` (no score: not analysed, no taste data, below the floor, not available, failed). Label `low_confidence` and `no_match` items as such.
- ★ The list comes in the order to show: `ranked` items by score, highest first, then `low_confidence`, then `no_match`, each of those two newest added first. Do not re-sort.
- LIST-1: the order uses stored scores only. It changes when a new analysis of a listed book finishes, not when the taste profile changes (the items then say `isOutdated`) and not while a new analysis is still running.

*Compare*
- `a` and `b` are full `Analysis` objects, the same as `GET /analyses/:id`. `traitDifferences` lists only the book traits whose values differ (compared as sets); an empty list on one side means that side's trait is unknown. Traits unknown on both sides are not listed.

*Delete my data* (SEC-3, D-022)
- Removes the reader's taste-profile versions with their ratings and questionnaire answers, rating imports, analyses with their steps and personal matches, feedback and the reading list. `onboardingState` becomes `pending`.
- Kept on purpose: the account (email, password, display name, sessions) and the scan and refresh counters, so limits cannot be reset by deleting data. Shared catalog rows and public review summaries belong to no reader.
- Ask for the password again before calling. After `204`, reload the reader (`GET /me`) and treat every cached result as gone.

## 5. Frontend rules that depend on this contract
- Render what the API returns. Never compute match, confidence, staleness or ordering.
- Every screen handles: loading, error (by `code`), empty, partial, failed.
- Show the disclaimer that the match reflects similarity to the reader's taste, not a probability of enjoyment.

## 6. Backend rules that depend on this contract
- Evidence IDs in `evidenceIds` must resolve (RES-5). Never return an ID that does not exist.
- Confidence is computed in code.
- Where a source forbids storing or displaying text, return only derived data and `excerpt: null`.
- Responses never contain secrets, password hashes, other users' data or stack traces.
